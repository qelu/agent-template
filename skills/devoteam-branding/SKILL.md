# Devoteam Branding

Apply the official identity without weakening the content brief, damaging native structure, or
editing an official source asset.

## Start with the task mode

Choose one mode before editing:

- **Create:** build new content in the best current official template.
- **Rebrand:** preserve the source's meaning and data while moving it into the official system.
- **Audit:** report concrete brand and layout defects; edit only when the user asks for changes.

Confirm the artifact type, target format, language, audience, internal/external use, print/screen
channel, deadline, and required partner or business-unit marks. Ask only for missing information
that materially changes the result.

## Resolve current official sources

1. Read [official-sources.md](references/official-sources.md).
2. Access the authenticated Devoteam Branding Zone or an official template supplied by the user.
3. Revalidate the relevant color, font, logo, and template guidance at task time. Treat the
   baseline in [brand-system.md](references/brand-system.md) as a fallback, not proof that the
   current official source is unchanged.
4. If official sources are unavailable, use a user-supplied approved template or asset. Otherwise
   ask whether to proceed with the dated fallback and disclose that limitation in the handoff.
5. Never expose, publish, or copy private source URLs, file IDs, access tokens, or internal content
   into the artifact or a public repository.

Apply this precedence order: explicit user content requirements; current official native template;
current Branding Zone rules; the dated fallback baseline. Report conflicts instead of silently
inventing a resolution.

## Build safely

1. Copy the complete official template and confirm the copy is distinct before writing. Preserve
   the official source and the user's original artifact.
2. Read [brand-system.md](references/brand-system.md), then exactly the guides required by the
   deliverables:
   - [documents.md](references/documents.md) for DOCX, Google Docs, CVs, reports, proposals, and
     document-origin PDFs;
   - [presentations.md](references/presentations.md) for PPTX and Google Slides;
   - [spreadsheets.md](references/spreadsheets.md) for XLSX and Google Sheets;
   - [other-artifacts.md](references/other-artifacts.md) for PDFs without a source, one-pagers,
     white papers, social assets, email signatures, video, and digital backgrounds.
3. Use the artifact-specific authoring skill or tool when available. This skill adds brand
   constraints; it does not replace format-native authoring and render verification.
4. Preserve masters, layouts, named styles, headers, footers, formulas, charts, validation,
   accessibility, editable objects, and semantic reading order. Replace every placeholder and
   stale project reference.
5. Retrieve the exact approved logo or badge at task time. Never redraw, trace, recolor, crop,
   stretch, or substitute one from memory.
6. Keep narrative text editable. Preserve aspect ratios for logos, photos, screenshots, charts,
   and diagrams.

## Validate before handoff

Render or preview every delivered page, slide, sheet region, or visual asset. Verify:

- the correct current template and approved assets were used, or the fallback is disclosed;
- no official source or user original was modified;
- content, formulas, links, citations, and data remain correct;
- no placeholder, sample, hidden, or prior-project content remains;
- typography and color roles follow the brand system with adequate contrast;
- logos are official, legible, undistorted, and appropriate for audience and channel;
- spacing, alignment, density, hierarchy, tables, charts, and images are readable;
- color is not the sole carrier of meaning and reading order remains accessible;
- the artifact opens in the requested native format and remains editable where expected.

Re-render after every material repair. State what was created or changed, which official source or
fallback governed the result, what validation ran, and any remaining limitation.
